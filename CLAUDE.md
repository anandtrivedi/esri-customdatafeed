# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

ArcGIS Custom Data Feed (CDF) provider that connects Databricks tables to ArcGIS Server as Feature Services. It's a Node.js plugin that runs inside ArcGIS Server's CDF runtime — not a standalone server.

Two backends: **Lakehouse** (Databricks SQL Warehouse, read-only, large-scale) and **Lakebase** (Databricks managed PostgreSQL + PostGIS, read+write, low-latency).

## Commands

```bash
# Install dependencies
cd nodejs-provider && npm install

# Run all tests (362 tests, ~5s)
cd nodejs-provider && npm test

# Run a single test file
cd nodejs-provider && npx mocha test/sql.test.js --timeout 5000

# Run tests matching a pattern
cd nodejs-provider && npx mocha test/model.test.js --timeout 5000 --grep "editData"
```

No build step — plain Node.js, no transpilation. No linter configured.

## Architecture

### Entry point and routing

`src/index.js` registers the provider with ArcGIS CDF runtime. `src/model.js` is the core — it implements the CDF interface methods: `getData`, `editData`, `authorize`, `getMetadata`.

**Backend routing in model.js:** if `req.params.lakebaseHost` is set, route to Lakebase (PostgreSQL); otherwise route to Lakehouse (Databricks SQL). Editing always goes through Lakebase.

### Module organization (`src/modules/`)

Modules split by backend. Import from `modules/index.js` (the barrel export), not individual files.

**Lakehouse (Databricks SQL):**
| Module | Purpose |
|--------|---------|
| `sql.js` | Builds SELECT queries from ArcGIS query params (where, objectIds, geometry, outFields, pagination, time, orderBy, distinct) |
| `geometry.js` | Spatial filter construction; DE-9IM compound expressions for ST_Overlaps and ST_Crosses (Databricks lacks these natively) |
| `geometryFormat.js` | Handles 4 geometry storage formats (WKT, WKB, GeoJSON, native GEOMETRY); auto-detects from column name or explicit config |
| `connectionPool.js` | Databricks SQL connection pool with min/max sizing, idle cleanup, wait queue with timeout |

**Lakebase (PostgreSQL + PostGIS):**
| Module | Purpose |
|--------|---------|
| `lakebaseQuery.js` | Builds PostGIS SELECT queries with parameterized `$1, $2` placeholders; all 6 spatial predicates native |
| `lakebasePool.js` | pg connection pool; auto-generates OAuth tokens from PAT via `/api/2.0/database/credentials`; 5-min refresh buffer before expiry |
| `editSql.js` | INSERT/UPDATE/DELETE SQL builders for applyEdits; parameterized; geometry converted Esri→GeoJSON→PostGIS |

**Shared:**
| Module | Purpose |
|--------|---------|
| `translate.js` | Row data → GeoJSON FeatureCollection; parses geometry JSON, casts BIGINT IDs via `Number()` |
| `sanitize.js` | SQL injection prevention: `validateFieldName`, `validateIdentifier`, `escapeSqlString`, `checkWhereClauseSafety`, `validateInteger` |
| `filters.js` | Generates `filtersApplied` metadata object for CDF runtime |
| `auditLog.js` | Optional JSON-lines audit logging (enabled via `ENABLE_AUDIT_LOG=true`) |

### Critical behavioral contracts

**SQL injection — two different strategies:**
- **Lakehouse** uses string interpolation. All user inputs MUST go through `sanitize.js` before interpolation. `checkWhereClauseSafety()` blocks DDL/DML keywords (DROP, DELETE, CREATE, INSERT, UPDATE, ALTER, TRUNCATE, GRANT, REVOKE, EXEC, EXECUTE, MERGE, UNION, SELECT, INTO), semicolons, subqueries `(SELECT`, and SQL comments (`--`, `/* */`). Word-boundary matching prevents false positives on column names like `updated_at`.
- **Lakebase** uses parameterized queries (`$1, $2`). Identifiers are validated but not parameterized (correct per SQL spec). WHERE clause from user still goes through `checkWhereClauseSafety()` since it's interpolated as raw text.

**Geometry type names:** `inferGeometryType()` must return GeoJSON type names (`LineString`, `Polygon`), NOT Esri type names (`Polyline`). The CDF FeatureServer handles Esri mapping. This was a bug that was fixed.

**ID field handling:**
- Databricks BIGINT returns as string — `translate.js` casts via `Number()`. Max valid OBJECTID is 2,147,483,647 (32-bit signed int).
- `idField` is always included in SELECT even if not in `outFields` (CDF runtime needs it for OBJECTID).
- In edits: INSERT skips idField (auto-generated by DB), UPDATE requires it in attributes (for WHERE clause), DELETE takes array of IDs.

**Pagination:** Both backends fetch `resultRecordCount + 1` rows to detect `exceededTransferLimit`, then pop the extra row before returning.

**CDF runtime compatibility:** `authorize()` and `editData()` support both calling conventions — 11.4 callback pattern `(req, callback)` and 12.0 async pattern (return/throw). `getData()` uses callback pattern (both versions).

**Config layering** (2 config surfaces for users):
- `.env` — Databricks connection credentials + operational tuning (pool sizes, timeouts, Lakebase, security). This is the only config file users need.
- `req.params` (per-service) — Table name, geometry column, idField, maxRecordCount, srid, lakebase settings. Set during `createService`. Overrides env var defaults.

### Spatial filter handling differences

**Lakehouse** (`geometry.js`):
- Converts Esri geometry formats (envelope, point, polygon, polyline) → GeoJSON → `ST_GeomFromGeoJSON()`
- ST_Intersects, ST_Contains, ST_Within, ST_Touches are native
- ST_Overlaps uses 5-condition DE-9IM compound: `ST_Dimension(A) = ST_Dimension(B) AND ST_Intersects AND NOT ST_Covers(A,B) AND NOT ST_Covers(B,A) AND NOT ST_Touches`
- ST_Crosses uses 5-condition DE-9IM compound with `ST_Intersection` dimension check (computationally heavy)
- CRS transformation: if `inSR` differs from `dbSR`, applies `ST_SetSRID()` then `ST_Transform()`

**Lakebase** (`lakebaseQuery.js`):
- All 6 spatial predicates are native PostGIS functions (no DE-9IM workarounds needed)
- Geometry filter is parameterized (`$N` placeholder with JSON string value)
- Same CRS transformation logic via `ST_Transform()`

### Geometry format handling (Lakehouse only)

`geometryFormat.js` has two-tier detection:
1. **Explicit config** (preferred): `geometryFormat` service parameter set to WKT/WKB/GEOJSON/GEOMETRY
2. **Name-based fallback**: column name containing `wkt`→WKT, `wkb`→WKB, `geojson`→GeoJSON, else→native GEOMETRY

Each format wraps differently:
- WKT: `ST_GeomFromText(col, srid)`
- WKB: `ST_GeomFromWKB(col, srid)`
- GeoJSON: `ST_GeomFromGeoJSON(col)` — does NOT accept SRID parameter (hardcodes 4326)
- GEOMETRY: uses column directly

### OAuth token lifecycle (Lakebase)

`lakebasePool.js` manages auto-refreshing tokens:
1. If `LAKEBASE_PASSWORD` env var is set, uses it as static credential (no refresh)
2. Otherwise: resolves Lakebase instance name via `/api/2.0/database/instances`, then generates token via `/api/2.0/database/credentials`
3. Tokens refresh proactively 5 minutes before expiry
4. On auth errors from idle pool clients, pool is destroyed and recreated on next request
5. Pool keyed by `"host:port/database"` — one pool per unique connection string

### Edit flow (Lakebase only)

`model.js editData()`:
- Processes adds, updates, deletes sequentially
- `rollbackOnFailure=true`: wraps all ops in BEGIN/COMMIT with ROLLBACK on any failure (uses `pool.connect()` for dedicated client)
- Error codes follow Esri convention: 1003=rolled back, 1017=insert failure, 1018=delete failure, 1019=update failure
- DELETE uses `RETURNING idField` to identify which rows were actually deleted vs not found

### model.test.js setup pattern

Copy this when adding model tests. model.js validates env vars on `require()`, so they must be set in `before()`:

```js
const proxyquire = require("proxyquire").noCallThru();

// Stubs prevent real DB connections
const connectionPoolStub = {
  initializePool: () => {},
  getPool: () => ({
    acquire: async () => ({
      id: "test-conn",
      session: {
        executeStatement: async () => ({
          fetchAll: async () => [],
          close: async () => {},
        }),
      },
    }),
    release: () => {},
  }),
  shutdownPool: async () => {},
};

// Lakebase stub supports configurable results + query logging
let lakebaseQueryResult = { rows: [] };
let lakebaseQueryLog = [];
const queryFn = async (sql, params) => {
  lakebaseQueryLog.push({ sql, params });
  let raw;
  if (Array.isArray(lakebaseQueryResult)) {
    raw = lakebaseQueryResult.shift() || { rows: [] }; // queue pattern for multi-step tests
  } else {
    raw = lakebaseQueryResult;
  }
  return { ...raw, rowCount: raw.rowCount ?? (raw.rows?.length || 0) };
};
const lakebasePoolStub = {
  getLakebasePool: async () => ({
    query: queryFn,
    connect: async () => ({ query: queryFn, release: () => {} }),
  }),
  shutdownLakebasePools: async () => {},
};

before(() => {
  process.env.DATABRICKS_SERVER_HOSTNAME = "test-host.databricks.com";
  process.env.DATABRICKS_HTTP_PATH = "/sql/1.0/endpoints/test";
  process.env.DATABRICKS_ACCESS_TOKEN = "test-token";
  process.env.LAKEBASE_PASSWORD = "test-lakebase-password";

  Model = proxyquire("../src/model", {
    "./modules/connectionPool": connectionPoolStub,
    "./modules/lakebasePool": lakebasePoolStub,
    dotenv: { config: () => {} },
  });
});
```

**Key testing patterns:**
- Lakebase result queue: set `lakebaseQueryResult = [result1, result2, ...]` and each `queryFn` call consumes one via `.shift()`
- `lakebaseQueryLog` captures all executed SQL+params for assertions
- Module-level tests use `build()` helper functions with spread-override defaults to reduce boilerplate
- No shared test utilities — helpers are defined inline per test file

### Test assertion patterns

```js
// SQL output checks
expect(sql).to.include("ST_Intersects(");
expect(sql).to.include("LIMIT 2001");            // fetchSize + 1
expect(sql).to.not.include("ST_Transform");       // same SRID, no transform

// Parameterized query checks
expect(params).to.deep.equal([1, 2, 3]);
expect(params).to.have.lengthOf(3);

// Sanitization checks — valid returns value, invalid throws
expect(validateFieldName("name")).to.equal("name");
expect(() => validateIdentifier("name;DROP")).to.throw(/Invalid/);
expect(() => checkWhereClauseSafety("1=1; DROP TABLE x")).to.throw();
```

## Service parameters

Defined in `cdconfig.json` (13 parameters). When creating a service via Admin REST API, all must be included — use empty strings for unused ones. The presence of `lakebaseHost` determines backend routing. `maxRecordCount` and `srid` can be set per-service (fallback: env var, then 2000/4326 defaults).

## Files to know about

- `cdconfig.json` — Provider manifest registered with ArcGIS Server. `editingEnabled: true` enables the `editData()` interface at the provider level. `arcgisVersion: "12.0.0"` targets the 12.0 manifest format, but CDF itself works on 11.4+ (11.4 added `applyEdits` editing, 12.0 added the `editingEnabled` property).
- `.env` / `.env.example` — Databricks credentials + operational tuning (pool sizes, timeouts, Lakebase, security). `.env.example` is the template. `.env` is gitignored.

## Gotchas discovered during audit

- **`resultRecordCount` is capped** to `maxRecordCountPerPage` (default 2000) in both Lakehouse and Lakebase paths. Users cannot request unbounded result sets.
- **Lakebase SSL**: `LAKEBASE_SSL_VERIFY` defaults to `false` (accepts any cert). The Databricks API helper also skips cert verification (`rejectUnauthorized: false`). Fine for Databricks-issued certs, but be aware in custom PKI environments.
- **Operation cleanup in model.js**: extent and query operations are closed in independent try-catch blocks so one failure doesn't prevent the other from being cleaned up.
- **`lakebasePool.js` token refresh**: Two concurrent requests can both see expired token and both refresh. This is benign in Node.js (single-threaded) — worst case is one wasted API call. NOT a race condition.
- **connectionPool.js "race conditions"**: Not real — Node.js event loop is single-threaded. `acquire()` finding and marking a connection `inUse` is atomic within a single tick.
